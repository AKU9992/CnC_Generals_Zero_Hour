# Модернизация движка: FPS, DirectX 12 и подготовка DLSS

## Текущее состояние

Цель: максимально возможный FPS отрисовки без ускорения игровой логики.
Новая графическая платформа: DirectX 12, x64. Полный нативный перенос ещё
не закончен; установленный `game.dat` не заменён. Отдельная FPS-сборка Win32
прошла 40 минут игры по отчёту пользователя. Рост FPS пока не измерен.

Собран переходный мост DX8 → D3D9On12 → DX12. Его GPU-тест прошёл в
3440×1440 и 3840×2160 с проверкой настоящего устройства D3D12 и цвета результата.
Отдельный проход NVIDIA DLAA также прошёл синтетический GPU-тест в обоих
разрешениях. DLAA к игре пока не подключён; подробности и границы проверки
описаны в [dlaa-integration.md](dlaa-integration.md).

В установленной Zero Hour обнаружено:

```ini
UseFPSLimit = Yes
FramesPerSecondLimit = 30
```

В `GameEngine::execute()` ожидание при этом лимите составляет примерно 32 мс.
Это объясняет потолок около 31–32 FPS, о котором сообщил пользователь. Это
не доказывает отсутствие других ограничений производительности.

`GameEngine::update()` вызывает обновления клиента, сети и игровой логики в
одном цикле. `GameClient::update()` также обновляет объекты, эффекты и интерфейс
перед отрисовкой. Простое увеличение общего лимита или отключение ожидания
может ускорить одиночную игру. Настройки установленной игры поэтому оставлены
на прежнем лимите до разделения логики и рендера.

## Что сделано

- Установлены Microsoft C++ Build Tools, Windows SDK 10.0.26100 и CMake.
- Собран и запущен отдельный x64 `D3D12Capabilities.exe`: аппаратное устройство
  выделенная видеопамять около 16063 MiB. Это проверка устройства, не игровой
  рендерер и не тест FPS.
- В обеих исходных версиях защищён расчёт ожидания от нулевого/отрицательного
  FPS и переполнения беззнакового интервала. При обычном лимите 30 FPS прежний
  интервал сохранён.
- Оценка среднего FPS теперь пропускает первую, нулевую и некорректную временную
  выборку вместо деления на ноль. Она влияет на оценку FPS для LOD, не снимает лимит.
- Добавлено отключённое по умолчанию журналирование времени кадра для будущей
  пересобранной версии. CSV показывает время общего `update()`, время после
  него до конца кадра и полный интервал; номер логического кадра записывается
  отдельно. Это CPU wall-clock измерение; время GPU отдельно не измеряется.

Для пересобранного исполняемого файла включить журнал можно переменной среды
`GENERALS_FPS_PROFILE=1`. Файл `FramePerformance.csv` создаётся в каталоге
пользовательских данных игры и перезаписывается при следующем запуске с
профилированием. CSV не появится у существующего розничного бинарника, который
не содержит добавленного кода. Запись лога сама добавляет небольшую нагрузку;
для итоговых замеров нужен также запуск с отключённым логом.

## Проверки

```powershell
.\tools\Build-NativeReadiness.ps1
.\tools\Test-NativeFrameTiming.ps1
.\tools\Probe-LegacyCompilation.ps1
```

Первые две проверки прошли: компиляция DX12-пробы с `/W4 /WX`, создание устройства,
проверки настоящего класса журналирования и выражения ограничения FPS для
Generals и Zero Hour в x86 и x64. Проверены выключенное профилирование, точное
значение переменной включения, формат CSV, согласованность времён, номера
логических кадров и границы лимита (-1, 0, 1, 30, 60, 500, 1000, 2000).

Проба компиляции настоящего `Main/WinMain.cpp` новым MSVC не прошла:

- В `GameMemory.h` повторно определены placement `operator new[]` и `delete[]`,
  которые уже определяет современная стандартная библиотека.
- В `STLTypedefs.h` требуется отсутствующий `<hash_map>` из старой STLport.
- В `BaseType.h` есть конфликт макроса `BitTest` с современным Windows SDK.

Это проверка одной единицы трансляции, не полная сборка. Пустые каталоги Miles,
GameSpy, STLport и zlib и отсутствующие библиотечные файлы остаются отдельными
препятствиями. В исходниках Zero Hour найдено 25 файлов с inline assembly;
они требуют проверки/замены при переходе на x64. Установка современного
Windows SDK не добавляет старый SDK DirectX 8 и сторонние SDK.

## Последовательность переноса

1. **Воспроизводимая сборка.** Современные проекты сборки, устранение конфликтов
   MSVC, сохранение поведения контейнеров/аллокаторов, подключение или замена
   отсутствующих зависимостей. Проверить исходные загрузку карты, сохранения и
   сетевую синхронизацию. Получить рабочий бинарник до масштабных изменений.
2. **Профиль кадра.** Одна и та же карта/камера: пустая сцена, большая армия,
   бой с эффектами. Замер CPU/GPU отдельно, медиана и p95/p99 времени кадра.
   Сравнить 1280×720, 3440×1440 и 3840×2160 при поддержке последнего драйвером.
3. **Разделение времени.** Логика и детерминированные команды — 30 тиков/с;
   отрисовка — независимая. Между тиками интерполировать состояния объектов и
   камеры. Проверить паузу, реплеи, ускоренную перемотку, сеть и CRC; ограничить
   догоняющие обновления при длинном кадре. Не переносить всю игровую логику на
   частоту монитора.
4. **Графический слой.** Устранить передачу типов и состояний DX8 за границу
   рендерера, перенести текстуры, буферы, материалы, fixed-function эффекты на
   HLSL, затем terrain, модели, тени, воду, частицы и интерфейс. Реализовать
   DX12-очереди, fences, descriptor heaps, barriers и swap chain. Сначала
   воспроизвести оригинальное изображение и измерить результат.
5. **DLSS Super Resolution.** Раздельные разрешения сцены и вывода, depth,
   корректные motion vectors для камеры/объектов, jitter, история предыдущего
   кадра и сброс истории при загрузке/смене камеры. UI рисовать после увеличения
   изображения. Проверять поддержку функции через SDK и сохранять обычный
   рендеринг, если функция недоступна.
6. **Frame Generation.** Отдельная последующая интеграция после стабильного SR.
   Сгенерированные кадры не увеличивают частоту симуляции. Проверять задержку,
   UI, pause/alt-tab, поддержку SDK/драйвера и работу без FG.

Изменение API само по себе не гарантирует роста FPS. Если большая армия
ограничена CPU/AI, DLSS Super Resolution не устраняет это ограничение. После
замеров оптимизировать конкретные участки: вызовы отрисовки, смены состояний,
загрузки текстур, видимость и работу CPU.

## Экспериментальная сборка для первого замера

6 октября 2026 получена отдельная Win32/DX8 сборка на фиксированной
общественной основе GeneralsGameCode с нашим режимом FPS и CSV-профилем.
Компиляция и линковка успешны; запуск и результат FPS пока не проверены.
Подробности, происхождение исходников и порядок сравнения:
[experimental-fps-build.md](experimental-fps-build.md).
Это промежуточный результат, а не завершённый перенос DX12/DLSS.

  поддержка API/устройства проверяется для конкретной функции; пример интеграции DX12.
- [Microsoft: установка MSVC](https://learn.microsoft.com/en-us/cpp/overview/acquire-msvc):
  официальная установка Build Tools и компонентов SDK.
